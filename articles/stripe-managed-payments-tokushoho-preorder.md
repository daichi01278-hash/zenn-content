Autonomous Studio は、AI エージェントが調査・開発・公開までを行い、公開・課金・削除などは人間のオーナーが承認する、という実験です。最初のプロダクトは [billshock](https://github.com/daichi01278-hash/billshock) で、OpenAI・Anthropic・Vercel・Cursor の利用料が急に増えたときに Slack や Discord へ通知するオープンソースの CLI と GitHub Action です。

CLI は無料です。ホスト版にお金を払う人がいるかを確かめるため、最初から予約販売を出す計画でした。この記事では、日本から世界中の購入者にどう売る形にしたかと、エージェントだけではできなかった部分をまとめます。

## 計画と、変わったこと

最初のアイデア文書(2026-10-08)では、「Hosted billshock」の waitlist と、Lemon Squeezy か Stripe の予約販売(個人 月 5 ドル、チーム 月 19 ドル)を置く計画でした。30 日後の判定には予約数が入っています(予約 3 件以上か waitlist 20 件以上、加えて利用の指標)。

翌日までに、3 つ変わりました。

- **Lemon Squeezy ではなく Stripe。** オーナーは Lemon Squeezy の登録も始めていましたが、ストア審査に数日かかることがあります。Stripe はすでに使える状態だったので、Stripe の Payment Links で組みました。
- **月額ではなく一回払い。** リンクは 5 ドルと 19 ドルの一回払いにしました。まだ存在しない製品の先行予約は、サブスクより一回払いのほうが説明しやすく、返金もしやすいためです。
- **公開したのは 5 ドルのリンクだけ。** チーム 19 ドルは、あえて waitlist のみです。サイト側は、決済 URL がない予約ボタンを「Join the waitlist」に変え、フォームのプランを選んだ状態(`plan=team`)にします。どちらの経路でも `click_preorder_<plan>` イベントを記録するので、関心はどちらでも数えられます。

## なぜ Managed Payments か

海外の人にソフトウェアを売ると、知らない国の売上税・VAT・GST の問題が出てきます。Stripe Managed Payments では Stripe が販売者(Merchant of Record)になり、税の部分を引き受けます。設定は次のとおりです。

- 事業の用途: SaaS
- 税込価格(購入者には 5.00 ドルと表示され、その金額を払う)
- Adaptive Pricing(決済画面で現地通貨表示)

オーナーが本番の決済画面を確認し、5.00 ドル、カードと Cash App Pay が表示されました。Stripe の商品名は「billshock」だけだったのを「billshock Hosted Indie – founding pre-order」に変え、領収書で何を買ったか分かるようにしました。名前を変えてもリンクは変わらないので、サイトの修正は不要でした。

## 特商法のページ

日本からネットで売るには、特定商取引法に基づく表記が必要です。日本語を先、英語を下に置いた 2 言語のページにしました([/legal](https://billshock-1el.pages.dev/legal?ref=zenn))。ガイドページと同じく、サイトのページ生成スクリプトから作っています。

内容は次のとおりです。

| 項目 | 書いた内容 |
|---|---|
| 販売事業者・運営統括責任者・所在地・電話番号 | 請求があった場合、遅滞なく開示します |
| メールアドレス | 連絡先を HTML の文字参照で記載(人には読めて、収集ボットには拾われにくい) |
| 販売価格 | 5 USD(税込)。購入ページに表示する金額 |
| 商品代金以外の必要料金 | なし。カード会社が外貨決済の手数料を請求する場合がある |
| 支払方法 | クレジットカードなど(Stripe による決済)、購入手続きの完了時 |
| 提供時期 | ホスト版の提供開始時(2027-01-31 までを予定)。それまでに始められなければ全額を自動で返金 |
| 返品・キャンセル | 提供開始前はいつでも全額返金。提供開始後は購入から 14 日以内なら全額返金 |
| 動作環境 | 最新版の主要ブラウザと、監視対象サービスのアカウント |

エージェントはまず下書きを作り、決める必要がある所に「要記入」「要決定」と印を付けました。下書きには「法律の専門家による確認ではない」こと、迷ったら消費者庁の「通信販売広告について」を確認することも書いています。オーナーが空欄を埋めるまで、公開はしませんでした。

## 難しかったこと

コードで難しい所はありませんでした。難しかったのは、人が決める・人がやる部分です。

1. **本人確認。** Stripe は、オーナーが本人確認書類を出すまで入金(payout)を止めます。決済画面は表示され支払いも受けられますが、お金はまだ Stripe から出せません。これは今も未完了です。
2. **どのメールアドレスを載せるか。** 下書きでは、個人のアドレスを公開しないよう専用アドレスを勧めました。オーナーは既存のアドレスを選び、ページでは文字参照にして収集を遅らせています。
3. **提供開始後の返金条件。** 開始前の「いつでも全額返金」は簡単でした。開始後はオーナーの判断で 14 日にしました。
4. **Stripe 側の記載をページに合わせる。** 下書きのチェックリストには、Stripe の商品説明にも同じ提供時期と返金条件を書く、という項目がありました。これは任意の残タスクのままです。
5. **コードに残った古い前提。** 週次メトリクスのスクリプトは、2026-10-14 に直すまで予約の確認先を Lemon Squeezy と書いていました。

## ここまでの結果

購入は 0 件です。2026-10-14 までの 1 週間で、サイトの `view_pricing` イベントは 6 件、waitlist の登録は 0 件でした。billshock は告知の投稿をしていない(2026-10-14 にオーナーが手動投稿をしないと決めた)ので、価格を見た人自体がほとんどいません。10 月の売上は 0 円です。

それでも、この仕組みの目的には合っています。運用費はかかりません(Stripe は決済があったときだけ手数料)。そして誰かが買えば、税・領収書・返金ルールはすでに整っています。予約の数は 2026-11-13 の 30 日目の判定で数えます。

## 日本から売る人へ

- 税のことを考える前に、Merchant of Record が必要かを確認する。Managed Payments なら数個の設定で済みました。
- 特商法ページは、自分にしか決められない所(連絡先と返金条件)をはっきり空欄にした下書きから作る。
- Stripe の商品名は分かりやすくする。購入者が領収書で見る名前です。
- 本人確認は早めに始める。お金の流れを止める唯一の手順です。

`npx billshock demo` でキーなしでも出力例を見られます。価格と特商法の表記は [billshock のサイト](https://billshock-1el.pages.dev/?ref=zenn)、コードは [GitHub](https://github.com/daichi01278-hash/billshock) にあります。
